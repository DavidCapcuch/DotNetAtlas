## Design decisions taken (with rationale)

- **Per-BC Health-Checks DI in `Catalog.Infrastructure.Common` (not platform)** — exact precedent: Basket. Keeps the connection-string pulls + KafkaOptions binding co-located with the BC's other persistence + messaging DI, and avoids inflating `Platform.ServiceDefaults` with config knowledge that varies per BC (e.g., Catalog uses `redis-cache` for idempotency, Basket uses `redis-basket` as primary store — different connection-string names).
- **Probe Schema Registry via `GET /subjects`, NOT `GET /`** — fixed during the Opus pre-commit review (see HIGH-1 below). `/` is not a documented Confluent SR endpoint and its 200 response is incidental on 7.x; `/subjects` is the canonical REST endpoint, returns `[]` on 200 even when no subjects exist, and is **the same path the schema-registry container's own compose-level healthcheck uses** (docker-compose.yaml:300) — drift across SR versions is caught uniformly.
- **`AddDbContextCheck<CatalogDbContext>` (not `AddNpgSql`)** — matches Basket. The `CatalogDbContext`'s configured `EnableRetryOnFailure` policy is honored by `Database.CanConnectAsync()`, so a transient Postgres flap doesn't trip readiness mid-flight.
- **`extra_hosts: localhost:host-gateway` + Authority kept as-is** — Keycloak's `--hostname=http://localhost:9011` (compose:731) bakes the issuer into every token. Three options were considered: (a) override `JwtBearer.Authority` to the in-network URL `http://keycloak:8080/...` and the API would then reject tokens because their `iss` claim mismatches, (b) override `MetadataAddress` separately, or (c) **map `localhost` inside the container to the host gateway** so `Authority=http://localhost:9011/realms/dotnetatlas` works as-is. Picked (c) because it requires zero code changes, no platform-side issuer-validation override, and Kestrel binds `0.0.0.0` (not `localhost`) so the in-container loopback rebind is harmless. The OAuth code path was not hit during smoke (read endpoints 401 anonymously, as designed); production verification remains a follow-up.
- **Host port `8100:8080`** — host port `8080` is taken by `nginx-cdn` (compose:687); the relay band `8090-8095` is fully occupied. `8100` is the next clean slot, leaving the `81xx` band for future BC APIs.
- **No new `HealthChecksOptions`-style timeout binding class** — Catalog's `appsettings.json:96-101` already has a `HealthChecks` section with four timeouts, but Basket's precedent (the chosen template) doesn't bind those to per-check `timeout:` arguments either. The section sits idle for now; wiring it would be a parallel cleanup, not M7's scope.
- **No catalog.api `healthcheck:` directive in compose** — the chiseled-extra base image has no `curl` / `wget` / shell, and the existing seven `outbox-relay-*` services in the same compose file (lines 354-622) — also chiseled — likewise have no `healthcheck:` block. Catalog matches the established repo pattern. The Opus reviewer flagged this (HIGH-3) but accepted it as a follow-up given the chiseled-image constraint and consistent precedent. Recommended longer-term fix: a self-contained healthcheck binary published alongside `Catalog.Api.dll`.

## Open questions / improvements proposed but NOT implemented

- **Wave-0 DB-bootstrap gap (BLOCKER for end-to-end Avro schema registration)** — `docker-compose.yaml:22` mounts only `./src/keycloak/init-db.sql` into Postgres's init dir; there's no per-BC database-creation script. As a result `psql -c '\l'` on a clean stack shows only `Weather + keycloak`, not `Catalog`. The `outbox-relay-catalog` container has been silently failing for the lifetime of the compose stack (`MessageText: database "Catalog" does not exist`, FATAL); the relay's restart policy keeps it crashing. M7 verified the smoke flow by manually creating the `Catalog` database, which proves wiring correctness. Two follow-ups belong to the platform / Wave 0 wave: (a) ship a Postgres init script that `CREATE DATABASE`s every per-BC database known to the realm, and (b) decide who applies the EF migrations on cold start (init container? `dotnet ef database update` step in the Dockerfile? feature-flagged auto-migrate at API startup?). Without (b), the `catalog.OutboxMessages` table doesn't exist either, so the relay-driven Avro auto-registration is end-to-end-pending even with (a).
- **catalog.md `<verification>` doc-correction (M8)** — two items: (1) port `localhost:8080` → `localhost:8100` (8080 is `nginx-cdn`); (2) the curls assume anonymous GET, which M6 broke by adding `RequireAuthorization("catalog.read")`. Either the doc gets updated to include a service-auth bearer-token fetch step, or the smoke step swaps to `GET /api/healthz` + `GET /api/readiness` (auth-free). M8's docs-self-correction milestone owns this.
- **catalog.api Compose `healthcheck:` follow-up (HIGH-3)** — recommended above; deferred.
- **Wave-level `HealthChecksOptions` timeout binding** — Catalog's `appsettings.json:96-101` carries unused timeout config. Either wire it (parallel to `Platform.OutboxRelay.WorkerService/Common/HealthChecksDependencyInjection.cs`), or remove it. Either way it's a cross-BC harmonization concern (Basket has the same dead config), not M7's scope.
- **OutputCache redis-cache instance-name namespacing** — `AddIdempotencyKeyOutputCache` already namespaces with `{serviceName}:idem:` so multi-service collision is impossible, but the readiness probe pings `redis-cache` as a whole. If multi-tenant prod ever needs per-service availability, the probe granularity may need to shift to "service's own keyspace reachable" — over-engineering for v1. Documented; no action.
