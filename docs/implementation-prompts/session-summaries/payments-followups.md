## Per-fix detail

### `870a745` — C-1: `IsRetryable` projection

- Root cause: `PaymentAuthorizationFailedMapper.cs:22-29` and `PaymentCaptureFailedMapper.cs:20-28` omitted the `IsRetryable` field on the Avro record initializer. The avrogen-generated `bool _IsRetryable;` defaulted to `false` for every emitted failure event on the infinite-retention `payments.transactions` topic. Saga retry-vs-compensate path was degraded; future per-reason buckets would key off bad data.
- Fix: co-located the retry-vs-compensate rule in `GatewayResponseClassifier.IsRetryable(FailureReason)`. v1 rule: only `GatewayTimeout` is retryable; `Unknown` is non-retryable so undefined gateway codes don't accidentally trigger retry storms.
- Test: extended `PaymentEventMapperTests` with a per-`FailureReason` theory pinning the expected projection on both failure mapper outputs.

### `c7f2b75` — H-Cond-2: FSM pre-check before gateway

- Root cause: `VoidPaymentCommandHandler.cs:69`, `RequestRefundCommandHandler.cs:69`, and `CapturePaymentCommandHandler.cs:72` invoked the gateway BEFORE the aggregate's FSM source-state guard fired. Saga-ordering bugs (e.g. Void against a Completed payment) reached the real PSP before the aggregate rejected the transition. Under stub gateway this is a no-op; against Stripe / Adyen / Braintree it's undefined behaviour on an already-captured authorization.
- Fix: inserted side-effect-free `if (!tx.Status.CanTransitionTo(target)) throw new DataIntegrityException(...)` between the idempotent short-circuit and the gateway call in all three handlers.
- Test: 3 new unit tests pin the gateway-untouched assertion (each handler × wrong-status aggregate). Integration test `Capture_WithoutPriorAuthorize_*` now asserts `Payments.InvalidStatusTransition` (was `Payments.MissingGatewayTransactionId`, now unreachable for this path — filed as [#250](https://github.com/DavidCapcuch/DotNetAtlas/issues/250)). Integration test `Void_AfterCapture_*` renamed to `_NoGatewayCall_NoStateChange` and `VoidCount` assertion flipped `1 → 0`.

### `9e2a94b` — H-8: wire `AuthorizationId` validation

- Root cause: `Capture` + `Void` Kafka commands carry `AuthorizationId` on the wire but the Payments-side handlers reloaded the value from `tx.GatewayTransactionId` and never validated it against the inbound value. Stale-token replays / saga bugs silently absorbed.
- Fix: `AuthorizationId` is now a required member on application `CapturePaymentCommand` / `VoidPaymentCommand` (propagated by `SagaCommandMappers`); handlers compare `tx.GatewayTransactionId` to `command.AuthorizationId` and throw `DataIntegrityException("Payments.AuthorizationIdMismatch")` on disagreement. KafkaFlow's poison classification routes the message to `payments.commands.DLT`.
- Test: 2 new unit tests (Capture + Void) + 1 new integration test `Void_AuthorizationIdMismatch_ThrowsDataIntegrityException_NoGatewayCall`. Existing integration tests updated to pass the real stored gateway token (`stub-{correlationId:N}`).

### `d9f8806` — H-6: `ExpiresAtUtc` via gateway response

- Root cause: `PaymentAuthorizedMapper.cs:39` synthesized `AuthorizedAtUtc + 7 days` inline even though the schema documented the field as the gateway-issued expiry window. Capture-deadline alerting would key off a fictitious value.
- Fix: added `ExpiresAtUtc` to `AuthorizeResponse`, threaded through `PaymentTransaction.Authorize(...)` → `PaymentAuthorizedDomainEvent.ExpiresAtUtc` → `PaymentAuthorizedMapper`. `StubPaymentGateway` now reads `TimeProvider` to return `now + 7 days` deterministically; the placeholder lives in the adapter rather than the mapper. v2 real adapters return the gateway's actual expiry. No aggregate persistence — the value is only needed at mapper time.
- Test: `StubPaymentGatewayTests` pin the populated `ExpiresAtUtc`. `PaymentEventMapperTests` passes a deliberately out-of-band `ExpiresAtUtc` to a regression that re-introduces inline synthesis fails loudly.

### `2e8fa42` — H-4: `IdempotencyKey` end-to-end

- Root cause: `AuthorizePaymentCommand.avsc` declares a required `IdempotencyKey` field documented as "Idempotency key to prevent duplicate authorizations." The Payments-side mapper dropped it; the application command had no corresponding property; nothing reached `IPaymentGateway.AuthorizeAsync`.
- Fix: wire it end-to-end. `IPaymentGateway.AuthorizeAsync` gains an `idempotencyKey` parameter; `StubPaymentGateway` rejects blank keys with `ArgumentException` so the contract is enforced uniformly; `CountingPaymentGateway` captures the last seen key for integration assertions.
- Test: new unit test pins the exact key reaches the gateway port. New integration test `Authorize_PropagatesIdempotencyKey_FromWireToGateway` exercises the full Avro → mapper → handler → gateway path. Validator gains "empty key fails" coverage.

### `7b21862` — H-3: persist `Requested` before gateway

- Root cause: a naive single-`SaveChanges` flow had a window where the gateway succeeded but `SaveChangesAsync` failed (DB blip, deadlock, concurrency violation); the inbox-dedup row rolled back, saga retries re-entered via `existing is null`, and the gateway got called a second time. Real PSPs issue a fresh authorization id per call and DO charge funds.
- Fix: split `AuthorizePaymentCommandHandler.HandleAsync` into two `SaveChanges` sites — first the aggregate-created `Requested` state (durable inbox-dedup + aggregate-row anchor BEFORE the gateway call), then the post-gateway transition. If the SECOND save fails, saga retry finds the existing `Requested` aggregate, skips the Create branch, and re-attempts only the gateway call + transition. Combined with H-4 (`IdempotencyKey` at the gateway port) the gateway-side has an independent dedup safety net.
- Test: existing happy-path assertion goes from `Received(1).SaveChangesAsync` to `Received(2)`. New `Handle_NewPayment_PersistsRequestedBeforeGatewayCall` test uses NSubstitute `Received.InOrder` to pin the SaveChanges → AuthorizeAsync → SaveChanges call order. New `Handle_SagaRetry_AggregateAlreadyInRequested_*` test exercises the recovery path.

### `eeb5069` — H-5: `Void Reason` end-to-end + Avro field

- Root cause: `VoidPaymentCommand.avsc` declared a required `Reason` field; the Payments-side mapper dropped it; the application command had no `Reason` property; the aggregate took no reason and emitted `PaymentVoidedDomainEvent` with no reason; the outbound `PaymentVoidedEvent` (Avro) had no `Reason` field. Audit-trail gap on a money-flow saga-compensation event. Asymmetric with the Refund flow which threads `Reason` all the way through.
- Fix: application `VoidPaymentCommand` gains required `Reason`; `SagaCommandMappers` propagates `avro.Reason → command.Reason`; `PaymentTransaction.Void(string reason, ...)` accepts reason; new `VoidReason` aggregate property persisted to `void_reason` column (user regenerated EF migration `20260522094454_Add_VoidReason_To_PaymentTransactions`); `PaymentVoidedDomainEvent.Reason` propagates to the mapper. Schema bump on `PaymentVoidedEvent.avsc` adds `Reason: ["null","string"]` default null — forward-compatible.
- Test: aggregate Void test now pins `tx.VoidReason` + event `.Reason` propagation. `PaymentEventMapperTests.PaymentVoidedMapper_MapsAllFieldsIncludingReason` covers the new field. `VoidPaymentCommandValidatorTests` covers `Reason` NotEmpty + length.

### `3dc0291` — H-7: doc-only collapse note + migration comment fix

- Root cause: migration `id` column comment said "Primary key (Guid v7 — time-ordered)." This is false on the v1 wire shape: the saga emits `AuthorizePaymentCommand` with only `CorrelationId`; the Payments-side mapper sets `PaymentId = avro.CorrelationId`, so the persisted PK is the saga's `Guid v4` (random), not a `v7`. B-tree index locality benefits of `v7` not realised.
- Fix: migration column comment, EF model config, snapshot, and designer files all updated to reflect the collapse. Added a § 2.1.1 subsection to `docs/bc-design/payments.md` spelling out v1 reality vs v1 design intent, downstream-consumer guidance, and the proper future fix path (saga emits fresh `v7 PaymentTransactionId` on the command — out of scope for Payments-followups, filed as [#255](https://github.com/DavidCapcuch/DotNetAtlas/issues/255)). Also added `CompletedAtUtc` + `VoidReason` rows to the § 2.1 property table (closes L-Cond-3 as a freebie).
- Test: no new tests — pure docs / comment edits. Unit + functional tests confirm EF model snapshot consistency (no `PendingModelChangesWarning`).

### `14dcaa2` — C-2: BREAKING `PaymentMethodId` uuid → string

- Root cause: `PaymentMethodId` on Payments-side wire schemas was declared as `{type:string, logicalType:uuid}`. The VO + BC chapter both define it as a 1-64 char gateway-issued opaque token (Stripe 'pm_…', Adyen alphanumeric, Braintree nonces — never a UUID). The constraint blocked any real-PSP adapter swap at the producer.
- Fix: `AuthorizePaymentCommand.avsc` (FULL_TRANSITIVE) and `PaymentRequestedEvent.avsc` (FORWARD_TRANSITIVE) both retyped `PaymentMethodId` → plain `string` (BREAKING). avrogen partials regenerated. Saga side expanded scope per user direction: `PaymentProcessingSagaState.PaymentMethodId` Guid → string; `PaymentInitiatedSagaEvent.PaymentMethodId` Guid → string; `PaymentProcessingSagaStateMap` column uuid → `varchar(64)` (user-generated saga EF migration `20260522121755_C2_PaymentMethodId_Uuid_To_String`). Boundary preserved at `CheckoutSagaOrchestrator.BuildPaymentRequestedEvent`: stringify via `saga.PaymentMethodId.ToString()` so upstream Basket/Ordering wire shapes (still Guid) keep working. Weather.Api dev endpoints retyped; integration test helpers now use Stripe-style `pm_*` tokens.
- Test: saga unit tests + Payments-side test slices all green. Architecture invariants intact.
