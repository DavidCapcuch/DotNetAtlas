# Feature flag providers: which to adopt

Research note (2026-08-09). Primary sources only — vendor documentation, vendor pricing pages, the actual GitHub repositories (LICENSE files, releases, source), nuget.org package pages, the OpenFeature specification, and the CNCF project page. No listicles, no vendor-authored competitor comparisons.

Every licence claim below was verified by fetching the **actual LICENSE file** (or GitHub's own licence detection on the correct default branch), not a marketing page. Every "latest release" and pricing figure was read on the page cited, on 2026-08-09. Where a page rendered no numbers, that is recorded in *Negative findings* rather than filled from memory.

Two provider-status claims were reached by inference and then **overturned by direct reads** — absence from `open-feature/dotnet-sdk-contrib` does not mean a vendor has no .NET provider, and presence in it does not mean the provider is community-maintained. See *Negative findings § Method*.

**Repo jurisdiction is already settled and is not re-decided here.** [ADR-0014](../adr/0014-feature-flags-openfeature.md) (Accepted 2026-04-19) chose OpenFeature with a local JSON-file provider, and it is implemented in [`Platform.ServiceDefaults/FeatureFlags/`](../../platform/Platform.ServiceDefaults/FeatureFlags/FeatureFlagsServiceCollectionExtensions.cs). This note asks the question ADR-0014 deferred: **which real provider goes behind that abstraction**, and it records two factual defects in ADR-0014 and one in the implementation.

---

## 1. The recommendation

**For this repo — stay on OpenFeature and put nothing behind it yet. When a real provider is needed, run [flagd](https://flagd.dev/) in docker-compose.**

The reasoning is specific to what DotNetAtlas *is*: a non-production reference solution whose stated profile ([ADR-0009](../adr/0009-reference-solution-target-profile.md)) explicitly does not require a SaaS feature-flag provider, and which every reader must be able to run on a laptop. Every commercial option fails that test at the first step — a reader would need to sign up for an account before `docker compose up` works.

flagd is the only candidate that is simultaneously: **Apache-2.0 with no vendor and no enterprise carve-out** ([repo metadata](https://api.github.com/repos/open-feature/flagd)), the **OpenFeature project's own reference daemon**, and shipped with a **first-class .NET offline mode** — `FLAGD_RESOLVER=file` reads flag definitions from a local JSON file, which is precisely the shape of the `flags.json` already committed here ([provider README](https://raw.githubusercontent.com/open-feature/dotnet-sdk-contrib/main/src/OpenFeature.Providers.Flagd/README.md)). The migration from today's custom `JsonFlagLoader` to flagd's file resolver is a schema alignment and a package swap, not a rewrite.

**The trade-off, stated plainly:** flagd has no UI, no audit log, no approvals, no RBAC and no hosted control plane. It is a *daemon*, not a platform — governance is whatever your Git repo and CI provide. For a reference solution that is a feature (the flag file is version-controlled and diffable, so reference scenarios are reproducible). For a production team that wants a non-engineer to flip a kill switch at 3am, it is disqualifying.

**The credible alternative — ConfigCat.** If the requirement shifts to "a real hosted product with a UI, that a .NET shop can actually buy": [ConfigCat.Client 10.0.0](https://www.nuget.org/packages/ConfigCat.Client) (published 2026-07-13, MIT) is the healthiest first-party .NET SDK in the set — `net462;netstandard2.0;netstandard2.1;net6.0;net8.0` with `IsTrimmable` and `IsAotCompatible` set ([csproj](https://raw.githubusercontent.com/configcat/.net-sdk/master/src/ConfigCatClient/ConfigCatClient.csproj)) — it evaluates locally from a polled config JSON, and its pricing is billed on flags and config downloads with **unlimited seats and unlimited MAU on every tier** ([pricing](https://configcat.com/pricing/), fetched 2026-08-09). For a 9-process topology that seat-and-connection-free axis matters more than the sticker price. Its cost: the OpenFeature provider is stale (see below), so you would bind the native SDK and lose some portability.

**Why not LaunchDarkly, the market leader.** Its .NET story is the best in the set — [LaunchDarkly.ServerSdk 8.16.0](https://www.nuget.org/packages/LaunchDarkly.ServerSdk) (2026-07-23, Apache-2.0, 79.5M downloads) plus a vendor-official OpenFeature provider. But its published unit is **"$10 per Service Connection / mo", where a service connection is one server-side SDK per environment per month**, plus "$8.33 per 1k client-side MAU / mo" ([pricing](https://launchdarkly.com/pricing/), fetched 2026-08-09). *My arithmetic, not theirs:* this repo has 9 flag-reading processes (7 bounded contexts + BFF + saga); across three environments that is 27 service connections ≈ **$270/month before a single user exists**. A microservice topology is the worst possible shape for that meter. This is a structural mismatch, not a quibble about price.

## 2. The OpenFeature question comes first, because it reframes everything else

**Adopt the abstraction. This repo already has, and that decision holds.** But the reasons that actually survive scrutiny are narrower than ADR-0014's.

**What OpenFeature is.** A CNCF **Incubating** project — accepted 2022-06-17, moved to Incubating 2023-11-21 ([CNCF project page](https://www.cncf.io/projects/openfeature/)). It specifies a flag-evaluation API, providers, hooks, evaluation context and tracking ([specification](https://openfeature.dev/specification/)).

**The argument for it that holds up:**

- **The failure semantics are specified, not per-vendor.** The spec requires that "Flag evaluation calls must always return the `default value` in the event of abnormal execution", and that client methods "MUST NOT throw exceptions, or otherwise abnormally terminate" ([flag evaluation § 1.4.10, 1.3.4](https://openfeature.dev/specification/sections/flag-evaluation/)). Every call site in this repo passes an explicit `defaultValue`, so provider-down degrades to a known branch rather than a 500. That guarantee is worth more than portability.
- **Telemetry is standardised and already free.** The .NET SDK ships `TraceEnricherHook`, `MetricsHook` and `LoggingHook` in the core package, and its [`TelemetryConstants`](https://raw.githubusercontent.com/open-feature/dotnet-sdk/main/src/OpenFeature/Telemetry/TelemetryConstants.cs) emit `feature_flag.key`, `feature_flag.result.variant`, `feature_flag.result.reason`, `feature_flag.provider.name` — the [OpenTelemetry feature-flag semantic conventions](https://opentelemetry.io/docs/specs/semconv/registry/attributes/feature-flag/) (currently Release Candidate stability). No vendor SDK gives you vendor-neutral OTel attributes for free.
- **Testing gets a real seam.** `InMemoryProvider` ships in the core `OpenFeature` package, and `Flag<T>` accepts a `contextEvaluator` delegate — `Flag(Dictionary<string,T> variants, string defaultVariant, Func<EvaluationContext,string>? contextEvaluator = null, ImmutableMetadata? flagMetadata = null, bool disabled = false)` ([source](https://raw.githubusercontent.com/open-feature/dotnet-sdk/main/src/OpenFeature/Providers/Memory/Flag.cs)) — so targeting rules can be exercised in tests without a network.

**The argument that does *not* hold up — "swap providers with a DI change".** ADR-0014 rests on this, and the evidence is weaker than it sounds. Portability is only as good as the specific .NET provider, and their health varies by two full orders of magnitude (table below). Three of the providers you would plausibly swap to are effectively dormant. Swapping is a DI change *only if* a maintained provider exists for the target — which for Optimizely, PostHog and AWS AppConfig it does not, in any state.

**The escape hatch that makes the abstraction genuinely durable is OFREP**, not the provider ecosystem. The [OpenFeature Remote Evaluation Protocol](https://openfeature.dev/specification/appendix-c/) is a vendor-neutral HTTP contract; where a backend speaks it, the generic [`OpenFeature.Providers.Ofrep`](https://www.nuget.org/packages/OpenFeature.Providers.Ofrep) (0.1.5, 2026-01-23) works against it and a dead vendor-specific provider stops being a blocker. Where a backend does not speak it, the vendor provider is the only OpenFeature path and its maintenance status becomes a hard dependency. **This is the single most decision-relevant axis in the whole comparison** and it is absent from ADR-0014.

**When you would bind directly instead.** If you pick a vendor whose value is its *analysis* rather than its flags — Statsig, Optimizely, GrowthBook, PostHog — the OpenFeature API surface only covers the evaluation call. Experiment assignment, metric logging and exposure events are all vendor-specific and sit outside the spec. Wrapping those in OpenFeature buys you portability for the 10% of the integration that was already portable. For those four, bind the native SDK and accept the lock-in knowingly.

### 3.4 Evaluation model and operational fit

| Provider | Model | Default refresh | Offline / bootstrap |
|---|---|---|---|
| flagd | Daemon, **or in-process**, **or file** (`FLAGD_RESOLVER`) | gRPC event stream; file poll 5,000 ms | **`FLAGD_OFFLINE_FLAG_SOURCE_PATH`** — first-class |
| DevCycle | Local bucketing (**WASM** via Wasmtime) or cloud | **SSE, 1 s poll fallback** — tightest in set | Code-supplied default only |
| ConfigCat | Local, polled config JSON | **60 s** auto-poll | `FlagOverrides.LocalFile(..., LocalOnly)` — strong |
| LaunchDarkly | Local, streamed ruleset | Streaming | File data source; Relay Proxy |
| Optimizely | Local, polled datafile | **5 min** | Datafile injection |
| Unleash | Local via `Unleash.Yggdrasil` core | **15 s** (code) — docs say 20 s | `UseBootstrapFileProvider` |
| PostHog | Local eval **is** supported in .NET | 30 s | Cached definitions survive outage |
| Azure App Config | Local, cached `IConfiguration` | Sentinel-key refresh | Cached config |

**Read the failure mode from the .NET source, not the docs.** Vendor documentation generally describes the JavaScript SDK's behaviour, and .NET diverges. Two verified-from-source examples: GrowthBook's JS SDK leaves every feature evaluating to `null` on network failure, while its **C# SDK serves stale from cache** (background refresh, logs and continues; blocks only when the cache is empty). Flagsmith's .NET client falls back to the last-known environment document, but with no cached document **and** no `DefaultFlagHandler` it **throws `FlagsmithAPIError`** — a genuinely different outage shape from "return the default". *Inference:* for this repo the OpenFeature spec's default-value guarantee (§ 2) papers over most of this, which is a further argument for the abstraction — but it papers over it only at the `IFeatureClient` boundary, not inside a provider's own initialisation path.

## 4. Per-provider notes

Only what the tables above do not already say.

### flagd — the recommendation
The OpenFeature project's own daemon, "a feature flag evaluation engine" usable "as a sidecar", "an engine running in your application process", or "as a central service" ([flagd.dev](https://flagd.dev/)). Latest `flagd/v0.16.1`, 2026-07-27. Flag definitions are JSON against a [published schema](https://flagd.dev/reference/flag-definitions/) with `state` / `variants` / `defaultVariant` / `targeting`; targeting is **JsonLogic** plus flagd operators `fractional` (deterministic bucketing), `starts_with`, `ends_with`, `sem_ver`. Sync sources include `file:`, `http(s)://`, `grpc(s)://`, Kubernetes CRD, `s3://`, `gs://`, `azblob://` ([sync configuration](https://flagd.dev/reference/sync-configuration/)). **Right call when** you want flags without a vendor, and Git is an acceptable governance layer. **Wrong call when** you need approvals, RBAC or a non-engineer UI — it has none.

### ConfigCat — the buy-it alternative
Targeting supports three condition types including **"Flag Condition (Prerequisite)"** ([targeting overview](https://configcat.com/docs/targeting/targeting-overview/)), and **zombie-flag detection** ships with both an email report and a [Zombie Flags API](https://configcat.com/docs/zombie-flags/) for CI. Governance: ISO/IEC 27001:2022 certified, **SOC 2 explicitly not claimed** ([trust center](https://configcat.com/trust-center/)); Terraform provider is Partner-tier and current (v5.8.1, 2026-07-15). No experimentation engine — A/B testing is percentage options plus an analytics hand-off. **Right call when** you want flags, not experiments, and seat-free pricing.

### LaunchDarkly — best .NET SDK, worst pricing shape here
Bucketing "generates a hash based on both the context key and context kind", partitioned 1–100,000 ([percentage rollouts](https://launchdarkly.com/docs/home/releases/percentage-rollouts)). *Inference:* because that hash is deterministic over inputs you supply, the same targeting key yields the same variation in every service — the page does not itself claim cross-service consistency. **Right call when** you are seat-and-service-light and want the deepest governance.

### Unleash — read the licence before self-hosting
Two decision-grade facts. **OSS caps at 1 project and 2 environments**, with RBAC beyond basic roles, change requests, SSO/SCIM, service accounts, flag dependencies and analytics all Enterprise-only ([OSS comparison](https://docs.getunleash.io/support/oss-comparison)). And **OSS Unleash Edge "is in LTS as of December 12, 2025" and "reaches EOL on December 31, 2026"** — roughly five months out — with the documented remedy being "migrate to an Enterprise plan"; streaming "is available on the Enterprise Edge build" ([Edge docs](https://docs.getunleash.io/unleash-edge)). Evaluation delegates to [`Unleash.Yggdrasil`](https://www.nuget.org/packages/Unleash.Yggdrasil) (1.3.1, 2026-06-24). **Right call when** you are buying Enterprise. The free tier is narrower than the "open-source feature management platform" description implies.

### Flagsmith — best test seam, three real gaps
The BSD-3 licence is the cleanest of the self-hostable set and its **Edge Proxy is free OSS with no tier gating** — a direct contrast with Unleash Edge's 2026-12-31 EOL. The test story is the strongest of any candidate: `OfflineMode = true` plus `LocalFileHandler("environment.json")` makes zero API calls and runs the **real** Flagsmith engine against a committed fixture, so segments, `% Split` hashing and multivariate weights all evaluate for real rather than being pinned flat. (*Inference:* the docs page on testing covers testing *in production*; offline-mode-as-fixture is read off the SDK's own test suite.)

Against that: **no flag prerequisites at all** — not gated, absent, with [Epic: Dependent flags](https://github.com/Flagsmith/flagsmith/issues/1674) open since 2022-11-18; real-time SSE is Enterprise-only *and* has no .NET client, so **60 s polling is the hard propagation floor for .NET**; and native experimentation is Enterprise Beta with JS/Python event collection only. Engineering hazards worth knowing: the client constructor does sync-over-async (`Task.Run(...).GetAwaiter().GetResult()`) when local evaluation is enabled — a thread-pool hazard if built eagerly in the DI graph — and it depends on Newtonsoft.Json and Polly 7 rather than System.Text.Json.

### DevCycle — freshest OpenFeature integration, newest owner
The provider is *in* the SDK, and OpenFeature was bumped to 2.14.0 on 2026-08-06 — no other vendor tracks the spec that closely. Counterweights: **DevCycle is now part of Dynatrace** (asset purchase, "as of January 13, 2026", [devcycle.com](https://devcycle.com/)); the SDK targets `netstandard2.0` only; local bucketing runs a **WASM core via Wasmtime**, whose trimming/AOT/musl behaviour under containerised .NET is unevaluated; and the Terraform provider has not shipped since 2023-03-29. Stale-flag tooling is the most granular in the set — four staleness classes plus a `dvc cleanup` CLI that rewrites evaluations and removes dead branches ([tech debt](https://docs.devcycle.com/best-practices/tech-debt/)).

### Statsig, Optimizely, GrowthBook, PostHog — experimentation platforms with flags attached
- **Statsig**: joined OpenAI, announced [2025-09-02](https://www.statsig.com/blog/openai-acquisition), continuing to operate. Flags at 0%/100% are unmetered — genuinely cheap for kill switches. .NET OpenFeature provider is community and dormant.
- **Optimizely**: the tell is in their own docs — a targeted delivery means "no decision events show up on the results page", and to measure you must "create an experiment… instead" ([flag deliveries](https://docs.developers.optimizely.com/feature-experimentation/docs/run-flag-deliveries)). The results pipeline is the product. **The C# `Decide` API is synchronous** (`public virtual OptimizelyDecision Decide(string key)` — [source](https://raw.githubusercontent.com/optimizely/csharp-sdk/master/OptimizelySDK/OptimizelyUserContext.cs)) and there is no `net8.0` TFM. Strongest governance on paper (SOC 2 Type 2 + ISO 27001/27017/27018 + PCI DSS for "Web & Feature Experimentation Services", [trust center](https://www.optimizely.com/trust-center/compliance/)) but **no vendor Terraform provider** and no OpenFeature provider in any language.
- **GrowthBook**: score it on two axes. As a *flag* tool it stands alone; as an *experimentation* tool it requires a connected data warehouse (BigQuery/Snowflake/Postgres/ClickHouse/…) or the paid Managed Warehouse at $0.03/1K events after 2M — and self-hosting requires **MongoDB**, infrastructure no other candidate imposes. The .NET path is the direct SDK (1.2.0, healthy, 2.6M downloads); the OpenFeature package (0.0.1) pins SDK 1.1.0, so adopting it silently forgoes the newer spec support and fixes. With **no OFREP fallback**, the realistic OpenFeature route is *a thin in-house `FeatureProvider` over `growthbook-c-sharp` 1.2.0* rather than the 0.0.1 shim — the same escape hatch applies to Unleash's two-commit community provider, and it is a better answer than either "use the shim" or "OpenFeature unavailable".
- **PostHog**: local evaluation *is* supported in .NET — "Local evaluation is only available in the Node, Ruby, Go, Python, C#/.NET, PHP, Java, and Rust SDKs" ([docs](https://posthog.com/docs/feature-flags/local-evaluation.md)) — but definition polls bill as "equivalent to **10 flags requests**". Prerequisite flags exist as [dependencies](https://posthog.com/docs/feature-flags/dependencies). RBAC is Enterprise-only. No .NET OpenFeature provider and no documented .NET test double.

### The .NET-native baseline: `Microsoft.FeatureManagement`
MIT, 4.6.0 (2026-07-01), 166.8M downloads — thoroughly healthy. `IVariantFeatureManager.IsEnabledAsync`, `[FeatureGate]`, `<feature>` tag helpers, and built-in filters `Microsoft.Percentage`, `Microsoft.TimeWindow`, `Microsoft.Targeting` ([reference](https://learn.microsoft.com/en-us/azure/azure-app-configuration/feature-management-dotnet-reference)).

**The trap: `Microsoft.Percentage` is not sticky.** [`PercentageFilter.cs`](https://raw.githubusercontent.com/microsoft/FeatureManagement-Dotnet/main/src/Microsoft.FeatureManagement/FeatureFilters/PercentageFilter.cs) decides with `result = (RandomGenerator.NextDouble() * 100) < settings.Value;` — **a fresh random draw on every evaluation**, so the same user flips in and out between requests. No Learn page says this; the reference only says the filter "provides a way to enable a feature based on a set percentage". `Microsoft.Targeting` *is* deterministic (SHA256 over the user id). **Rule: `Microsoft.Percentage` for stateless sampling only; `Microsoft.Targeting`, or variant `percentile` + `seed`, for any actual rollout.** This matters directly here — it is the exact mistake ADR-0014's `catalog.show-discontinued-in-search` flag is trying to avoid.

**Telemetry is OTel *transport* but proprietary *semantics*.** The library emits an `ActivityEvent` named `FeatureFlag` on `ActivitySource "Microsoft.FeatureManagement"`, tagged with Microsoft's own PascalCase names (`FeatureName`, `Enabled`, `Variant`, `VariantAssignmentReason`, `TargetingId`) — not the `feature_flag.*` OTel semantic conventions the OpenFeature SDK emits. Collectable, but no dashboard expecting semconv will understand it without remapping. The only first-party telemetry package is App-Insights-specific.

**It does not lock you out of OpenFeature** — [`OpenFeature.Contrib.Provider.FeatureManagement`](https://www.nuget.org/packages/OpenFeature.Contrib.Provider.FeatureManagement) bridges it (note the ID is singular `Provider`), though only at 0.1.2-**preview**. Two real limits: variants and telemetry require the newer `feature_management` schema — "Starting with version 4.0.0 of the library, new features, including variants and telemetry, aren't supported in the .NET feature management schema" — and there is no evaluation-context concept as rich as OpenFeature's, which is exactly ADR-0014's stated reason for preferring OpenFeature and it remains correct.

### Azure App Configuration and AWS AppConfig
Both are configuration services with a flag shape bolted on, and **neither has any .NET OpenFeature provider** — Azure has no ecosystem dataset entry at all, AWS has only a community `awsssm` (Parameter Store) entry for JS and Go, and AppConfig has **no official provider in any language**. Choosing either means binding to the cloud SDK.

**Azure** is the more natural fit for a .NET shop, because `Microsoft.FeatureManagement` is the same library either way and evaluation stays fully in-process — the provider hydrates `IConfiguration` and refreshes flags on a **30 s default interval**, so request volume tracks polling, not traffic. Two sharp edges: `AddAzureAppConfiguration(..., optional: true)` boots the app with *zero* flags if the store is unreachable, which silently turns every `IsEnabledAsync` to `false` — a mass kill-switch; and because evaluation is local, the whole ruleset including targeted user names ships to wherever evaluation happens.

**AWS AppConfig's targeting is stronger than its reputation** — correcting an assumption worth stating. The rule language includes a `split` operator that "Evaluates to `true` for a given percentage of traffic **based on a consistent hash of the provided context value(s)**", written `(split pct::10 by::$userId seed::"abc")`, where a supplied `seed` makes bucketing consistent "across feature flags, configuration profiles, and AWS accounts" ([rules and operators](https://docs.aws.amazon.com/appconfig/latest/userguide/appconfig-creating-multi-variant-feature-flags-rules-operators.html)). That is genuine deterministic per-user bucketing, and the cross-account seed guarantee is *better* than most vendors document. What it lacks is first-class reusable named segments.

**The .NET-decisive AppConfig constraint is the agent.** "For performance reasons, AWS CLI and SDK calls to AWS AppConfig don't retrieve variant data" ([multi-variant flags](https://docs.aws.amazon.com/appconfig/latest/userguide/appconfig-creating-multi-variant-feature-flags-procedures.html)) — so `AWSSDK.AppConfigData` cannot do multi-variant targeting at all. The sidecar agent (default poll 45 s, port 2772) is **mandatory, not an optimisation**, and it is what resolves variants. Note also the pricing asymmetry: $0.20 per million configuration *requests* versus $800 per million configuration *receipts* — a 4000× gap that is the whole economic argument for the agent's in-memory cache.

## 5. What this repo would actually do

Everything in this section below the first paragraph is **my inference**, not vendor guidance.

**Verified current state.** `OpenFeature` and `OpenFeature.Hosting` are pinned at **2.13.0** in [`platform/Directory.Packages.props`](../../platform/Directory.Packages.props) (and `OpenFeature` 2.13.0 in the `services/` and `saga/` files); latest is **2.14.0** (2026-06-22). [`AddFeatureFlags`](../../platform/Platform.ServiceDefaults/FeatureFlags/FeatureFlagsServiceCollectionExtensions.cs) registers an `InMemoryProvider` hydrated by [`JsonFlagLoader`](../../platform/Platform.ServiceDefaults/FeatureFlags/JsonFlagLoader.cs) plus the built-in `TraceEnricherHook`. Three flags are read: `catalog.show-discontinued-in-search` in `SearchProductsQueryHandler`, `bff.home-page-eager-cache-warm` in `HomePageCacheWarmer`, `checkout.payment-then-stock` in the checkout saga.

**Three defects worth fixing before choosing any provider** — these are repo findings, verified by reading the files:

1. **The percentage rollout does not roll out.** `flags.json` carries a `targeting` block with `{"op": "percentage", "attribute": "targetingKey", "value": 10}`, but `JsonFlagLoader.FlagFileEntry` declares only `State`, `Variants` and `DefaultVariant` — there is no `Targeting` property, so the block is silently dropped, and `Flag<bool>` is constructed without the `contextEvaluator` the SDK supports. `state` is parsed but never passed to the `disabled` parameter either. ADR-0014's headline "gradual rollout" showcase currently always returns `off`.
2. **No targeting key is ever supplied.** `SearchProductsQueryHandler` calls `GetBooleanValueAsync(key, defaultValue: false, cancellationToken: ct)` with no `EvaluationContext` — so even once (1) is fixed, there is nothing to bucket on.
3. **Tests work around process-global state that the SDK now solves.** `BffTestHostExtensions.UseWarmFlag` and Catalog's `IntegrationTestFixture` both substitute `IFeatureClient` with NSubstitute, and the comment says why: "OpenFeature's `Api.Instance` provider is process-global, so several fixtures sharing it would contaminate each other's flag reads." **SDK 2.13.0 — already the pinned version — added `Api.CreateIsolated()`**, "a fully independent `Api` instance, with its own providers, context, hooks, and event handlers", explicitly for testing and DI ([PR #740](https://github.com/open-feature/dotnet-sdk/pull/740)). Switching to an isolated instance seeded with `InMemoryProvider` would let integration tests exercise **real targeting rules** instead of pinning a flat boolean through a mock — which is the difference between testing the flag and testing the substitute.

**Where a provider would sit.** Keep `AddFeatureFlags` as the single seam in `Platform.ServiceDefaults`; it is already the right shape. Each of the 9 processes evaluates in-process — do **not** put flag evaluation behind the BFF and pass results downstream, because the saga and the Kafka consumers evaluate outside any HTTP request and would have no source.

**Cross-service consistency for one checkout** is the genuinely hard part, and it needs two things the repo does not have yet:
- **Propagate the targeting key.** ADR-0014 already specifies `TargetingKey = buyerId` for user flags and `orderId` for workflow flags; that must actually be attached at every call site and carried across the Kafka hop alongside the correlation ID. Deterministic bucketing is only consistent if every service hashes the same key.
- **Pin the ruleset version.** Even with the same key, two services on different ruleset versions can disagree mid-checkout. `feature_flag.version` and `feature_flag.set.id` exist in the OTel conventions precisely so you can *detect* this; nothing prevents it. For `checkout.payment-then-stock`, which changes step order, the safe pattern is to evaluate **once** at saga start and persist the decision on `CheckoutSagaState`, rather than re-evaluating at each transition.

**Concrete package moves, if flagd is adopted:** add `OpenFeature.Providers.Flagd` (0.7.2) to `platform/Directory.Packages.props`, run flagd in the existing `docker compose --profile full` stack, and point local/test runs at `FLAGD_RESOLVER=file` against the committed flag file. That keeps the zero-infrastructure property ADR-0014 required while replacing the hand-rolled loader with an evaluator that actually implements targeting. Note the older `OpenFeature.Contrib.Providers.Flagd` is **deprecated on NuGet** in favour of the un-prefixed ID.

**Testing.** Prefer `Api.CreateIsolated()` + `InMemoryProvider` with a `contextEvaluator` over substituting `IFeatureClient`; it removes the process-global hazard *and* exercises rules. Keep the substitute only where a test genuinely wants a flat value. Worth noting for provider selection: a test double that ignores evaluation context — Unleash's `FakeUnleash` discards it — pins on/off values while proving nothing about targeting.

## 6. Negative findings

**Method — two inferences that were wrong, and the fix.**
- **Absence from `open-feature/dotnet-sdk-contrib` does not mean no .NET provider exists.** GrowthBook and DevCycle both host vendor-official .NET providers outside contrib; enumerating contrib alone reports them as missing. Corrected by direct read of [the repo](https://api.github.com/repos/growthbook/growthbook-openfeature-provider-dot-net) and [the DevCycle docs](https://docs.devcycle.com/sdk/server-side-sdks/dotnet/dotnet-openfeature).
- **Presence in contrib does not mean community-maintained.** ConfigCat's and Flagsmith's .NET providers live in contrib and are `vendorOfficial: true`; Unleash's and Statsig's live there and are `vendorOfficial: false`. Repo ownership is not the signal.
- **The fix:** `openfeature.dev/ecosystem` is an Algolia-driven SPA that returns only nav chrome to a fetcher. The data behind it is plain `.ts` under `src/datasets/providers/` in [open-feature/openfeature.dev](https://github.com/open-feature/openfeature.dev) and is the only uniform answer to first-party-vs-community. Every `vendorOfficial` value in § 3.1 came from there.

**Two factual errors in ADR-0014**, which should be corrected when it is next revised:
- It states OpenFeature is "a **CNCF-graduated** spec". It is **Incubating** — accepted 2022-06-17, Incubating since 2023-11-21 ([CNCF](https://www.cncf.io/projects/openfeature/)). No CNCF page describes it as graduated.
- Its Implementation Notes sample chains `.AddInMemoryProvider().AddFileProvider(config[...])`, and the migration sample calls `.AddLaunchDarklyProvider(sdkKey:)`. Neither is a real API — there is no `AddFileProvider` in the OpenFeature .NET SDK, and LaunchDarkly's provider is registered by constructing `LaunchDarkly.OpenFeature.ServerProvider`. The shipped code does neither, so this is a doc defect only.

**Attribution.** The canonical feature-toggle taxonomy hosted on martinfowler.com is authored by **Pete Hodgson**, not Martin Fowler — [Feature Toggles (aka Feature Flags)](https://martinfowler.com/articles/feature-toggles.html), 2017-10-09. Its two axes (longevity, dynamism) and its inventory framing — "Savvy teams view their Feature Toggles as inventory which comes with a carrying cost and seek to keep that inventory as low as possible" — are the right frame for the lifecycle discipline ADR-0014 § Lifecycle already prescribes.

**Pricing that could not be verified from a primary page.**
- **Azure App Configuration** renders every figure as a `$-` placeholder on [its own pricing page](https://azure.microsoft.com/en-us/pricing/details/app-configuration/); only quotas are readable (Free 10 MB / 1,000 req per day; Developer 500 MB / 6,000 per hour; Standard 1 GB / 30,000 per hour; Premium 4 GB / unlimited; SLA 99.95% / 99.99%). The figures in § 3.3 therefore come from a **different first-party surface** — Microsoft's Azure Retail Prices API, queried for USD/eastus — and are region-specific; Premium was observed between $4.80 and $12.00/day depending on region. Microsoft also contradicts itself on the free-tier store count: [service limits](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/azure-subscription-service-limits) says 3 per region, the [FAQ](https://learn.microsoft.com/en-us/azure/azure-app-configuration/faq) says one.
- **AWS AppConfig has no "per hour of active deployment" charge** — an assumption worth discarding. The only hourly dimension is **$0.90 per *experiment* hour**. The page also carries no footnote defining "configuration request" versus "configuration received", so the 4000× gap between them is read off the `GetLatestConfiguration`-returns-empty-when-unchanged contract rather than a pricing definition.
- **Optimizely publishes no numbers at all.** [optimizely.com/pricing](https://www.optimizely.com/pricing/) shows no tiers and no dollar figures: "Every Optimizely plan is individually packaged." Their own support article routes back to the same page. A free tier exists, limited to one concurrent experiment. Everything above it is contact-sales.
- **Contact-sales-only tiers:** LaunchDarkly Enterprise, ConfigCat Enterprise and Dedicated, Unleash Custom Enterprise, Flagsmith Enterprise, GrowthBook Enterprise (cloud and self-hosted), Statsig Enterprise, DevCycle Enterprise, Flipt Enterprise.
- **ConfigCat's pricing page has a client-side monthly/annual toggle** whose state could not be confirmed; the figures in § 3.3 are whichever state was served. Also, the marketing page's bare "10 Feature Flags" understates the scoping — [the docs limits table](https://configcat.com/docs/subscription-plan-limits/) shows it is 10 flags **per product** and 10 configs per product.
- **Flipt's two first-party pages disagree**: the pricing page advertises annual billing as "Save 20%" while the v2 README quotes "$200/month or $2,000/year", a 16.7% discount. Neither is treated as authoritative here.

**Licences more restrictive than the marketing implies.**
- **Unleash** describes itself as an "Open-source feature management platform"; the server is **AGPL-3.0** as of 2026-05-26, and OSS is capped at 1 project / 2 environments with Edge reaching EOL 2026-12-31.
- **Flipt** presents as open source; its shipping branch is **Fair Core**, source-available with a competing-use ban and a two-year delay to MIT.
- **GrowthBook**'s proprietary boundary starts at **Pro**, not Enterprise.
- **PostHog** self-hosting is officially unsupported by its own vendor.

**Two self-hostable components ship with no licence file at all.** [`statsig-io/statsig-forward-proxy`](https://api.github.com/repos/statsig-io/statsig-forward-proxy) returns `license: null`, and `splitio/splitd` likewise reports `license: none`; neither repository root contains a LICENSE file and neither README carries licence text. **No licence means all rights reserved** — for anything that would be vendored or deployed, that is a legal blocker rather than a footnote. (`splitio/split-proxy` is not a public repo at all; the Proxy ships only as a Docker image, so no licence could be fetched for it.)

**Two repository traps that make a healthy SDK look dead, or a date wrong.**
- `launchdarkly/dotnet-server-sdk` is **archived** — "Development has moved to [dotnet-core]" — and its last release there was v8.5.1 (2024-06-03). The live package is built from [`launchdarkly/dotnet-core`](https://github.com/launchdarkly/dotnet-core). Similarly `splitio/dotnet-client` publishes **tags but no GitHub Releases** and its default branch is `development`, not `main`; reading /releases or `main` reports abandonment where there is none. Flipt's default branch is `v2` while `main` holds the old GPL v1 line.
- **GitHub's rendered `/releases` page omits the year for current-year releases**, and summarising fetchers guess it wrong. Every release date in this note was taken from the GitHub REST API `published_at` or from nuget.org, never from rendered release HTML.

**Governance gating is not uniform enough for a single column.** It is gated by *tier* for Unleash, LaunchDarkly (prerequisites, scheduled changes and approvals are each "only available to customers on select plans"), Statsig (custom RBAC is Enterprise) and PostHog (RBAC is Enterprise); by *deployment model* for GrowthBook; and by *which binary you run* for Flagsmith. Terraform maturity splits three ways too: ConfigCat, LaunchDarkly and Flagsmith are registry **partner** tier; Statsig and Harness publish from their own org but at **community** tier; GrowthBook has only a third-party community provider; **Optimizely has no vendor provider at all**; DevCycle's is partner-tier but has not shipped since 2023-03-29.

**Claims searched for and not found in a primary source** (recorded as not-found, not as absent): scheduled/temporary flags and change-request approvals for ConfigCat; prerequisite flags for Optimizely and DevCycle; audit-log retention and plan gating for DevCycle and Unleash OSS; a .NET-specific offline test provider for DevCycle and PostHog; Flipt v2 audit-logging mechanics (sold on the Enterprise pricing tier but absent from the v2 configuration reference, and `docs.flipt.io/v2/configuration/auditing` 404s); SOC 2 attestation for Flipt and Unleash. **GrowthBook OFREP support** is a qualified negative — org-wide code search, the `growthbook-proxy` repo, and [the proxy docs](https://docs.growthbook.io/self-host/proxy) all return nothing; its remote evaluation is a proprietary contract posting to `{apiHost}/api/eval/{clientKey}`.

Also unresolved: SOC 2 **Type I vs Type II** for GrowthBook (docs say only "SOC2"); audit-log retention for GrowthBook, Flagsmith and DevCycle; minimum MongoDB version for GrowthBook self-host and minimum PostgreSQL version for Flagsmith; whether Redis is required or optional for Flagsmith (its docs contradict each other across pages); and Harness's SOC 2 **Type II** specifically — [harness.io/security](https://www.harness.io/security) says only "SOC 2 compliant". Flagsmith publishes **no docs-hosted OSS-vs-paid matrix** — `docs.flagsmith.com/version-comparison` 308-redirects to the marketing pricing page, so that boundary had to be assembled from four separate pages.

**Docs-vs-source contradictions found, reported rather than smoothed over.** Unleash's .NET poll interval is **15 s** in `UnleashSettings.FetchTogglesInterval` while the README and `docs.getunleash.io/sdks/dotnet` both say 20 s. Flagsmith's csproj is `netstandard2.0` only with `LangVersion 8` while the docs claim ".NET Core 6.0+". GrowthBook's target framework is unsettled three ways — csproj says single-target `net8.0`, NuGet reports net8.0 + netstandard2.0, the README claims ".NET 8+ / .NET Framework 4.6.2+". Flagsmith's .NET HEAD is ~8 months ahead of its last release (v9.0.0, 2025-12-05), and an unreleased fix — [#189, "respect rule type for sub-rules in segment evaluation"](https://github.com/Flagsmith/flagsmith-dotnet-client/pull/189), merged 2026-05-15 — means released v9.0.0 evaluates nested segment sub-rules incorrectly with no released fix.

**Summarizer output that was caught and discarded rather than laundered into the note.** A page-summarizing fetch computed $0.0000002 × 1M as "$0.0002" for AWS (correct: $0.20); another answered "yes" to whether `[FeatureGate]` supports variants by conflating it with `RequirementType` (the constructor list has no variant overload); another mis-dated two Statsig releases by a full year because GitHub's rendered `/releases` page omits the year for current-year releases. Each was caught by contradiction with a second first-party surface. Where a fetch returned hedged phrasing ("common condition keys include…") it was treated as unfetched.

**Discarded.** `api.nuget.org/v3/registration5-semver1/openfeature/index.json` reported OpenFeature 2.1.0 / Nov 2024 as latest; both [nuget.org](https://www.nuget.org/packages?q=OpenFeature) and the [GitHub releases page](https://github.com/open-feature/dotnet-sdk/releases) agree on **2.14.0 / 2026-06-22**. The registration-index figure was a paging artifact and is not used. Separately, `OpenFeature.Contrib.Hooks.Otel` (0.2.0) and `OpenFeature.DependencyInjection` (2.9.0) are both **marked deprecated on NuGet**, superseded by the core SDK's built-in hooks and by `OpenFeature.Hosting` respectively — this repo already uses the correct successors.

**Dropped from scope.** Nothing in the requested set turned out to be dead. **Split and Harness FME are one product** (Harness acquired Split) but remain two separate ecosystem entries with different .NET stories — Split's provider is vendor-official and current (2026-06-25) while the Harness entry has no .NET provider at all, so they are listed as separate rows rather than merged.
